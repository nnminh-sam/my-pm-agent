Playbooks & Lifecycle

One set of SDLC playbooks (rules, skills and hooks, shipped as Claude Code plugins) that every repo can use, plus a lifecycle for each project in my_pm that tracks which stage each milestone is in and tells you what to do next across all your projects.

Summary

  • Playbook is the reusable definition: principles, stages, checks, and the rules, skills and hooks that carry them out. Each one is a Claude Code plugin: a base sdlc playbook plus a personal overlay and a company overlay.
  • Lifecycle is one project's live state against its playbooks. It lives in my_pm next to projects, milestones and tasks, and is computed by a pure, tested engine like the scheduler.
  • Hooks connect each repo to my_pm. At session start you get a short brief (stage, open checks, next action, rules for this stage). Test runs and repo changes flow back as signals.
  • The lifecycle grows. Detectors add checks when the repo changes shape, retros add project-specific checks, and checks that prove general get promoted into the playbook for every project.
  • Build it in slices. PMA-M5 (lifecycle core in my_pm) is useful on its own: any Claude session can ask “what's next across my projects?”

What exists today

What I found in my_pm, your other repos and the current Claude Code docs.

  • my_pm already answers “what next?” for tasks. It has the deterministic scheduler, MCP tools and prompts (breakdown_milestone, work_on_task, replan), and priority and deadline inheritance in hierarchy.ts. It has no idea of process stage.
  • You've built this plugin shape before. rnd-tools is a marketplace with a deterministic engine plus skills, agents and hooks. The playbooks repo can copy its layout, Makefile and evals.
  • The stage skills already exist. software-engineering-orchestrator has to-spec, grilling, domain-modeling, tdd, implement, code-review and diagnosing-bugs. The playbook wraps them instead of rewriting them.
  • “Workflow” is taken. In Claude Code a workflow is a JS script that orchestrates subagents (/workflows, and a workflows/ folder in plugins). This proposal uses playbook and lifecycle instead. A playbook can still include a Claude Code workflow, for example a review fan-out during verify.
  • Plugins can't ship rules. A plugin can't load CLAUDE.md or .claude/rules files into context. Rules have to arrive through a hook, a skill, or files copied into the repo (see Where rules come from).

Base playbook: stages and their exit checks

Every milestone runs the loop. A milestone leaves a stage when its exit checks pass or you waive them with a reason. The principles stay fixed; the checks under them can grow.

Check kinds: auto is computed from my_pm data (all tasks estimated, all done). probe comes from repo signals (test runs). attest is recorded by you or an agent, with evidence.

Covers your first need: workflows made of rules, skills and hooks, reusable across company and personal projects.

playbook.yaml

name: sdlc
version: 1.0.0
principles:
  clarity:    No build without an accepted spec
  verified:   Nothing ships unverified
  reversible: Every release can be rolled back
  learn:      Every release feeds back
stages: [idea, spec, design, plan, build, verify, release, learn]
checks:
  spec.accepted:    { stage: spec,    principle: clarity,  kind: attest, skill: spec }
  plan.estimated:   { stage: plan,    kind: auto }   # all tasks estimated, none > max_task_hours
  build.tasks_done: { stage: build,   kind: auto }
  verify.tests:     { stage: verify,  principle: verified, kind: probe }
  verify.review:    { stage: verify,  principle: verified, kind: attest, skill: verify, task: { estimate: 0.5 } }
  learn.retro:      { stage: learn,   principle: learn,    kind: attest, skill: retro }
detectors:
  - when: { exists: migrations/ }
    add:
      release.migration_paired: { stage: release, principle: reversible, kind: attest,
        text: "Migration applied to prod in the same cut-over as the deploy; rollback point recorded" }
    rules: [db-migrations]
guards:
  code_before_spec: ask        # off | warn | ask

An overlay says extends: sdlc and adds checks, detectors or rules, for example verify.security_review or release.ticket_linked for company work. A task: on a check means entering its stage creates a real task in my_pm, so the scheduler plans it.

Lifecycle in my_pm

Covers your second need: each project's status and what to do next. It follows my_pm's existing architecture: a pure engine with tests, persistence through Repository, and MCP tools.

Per CLAUDE.md: add the fields to the zod schemas in types.ts (key order is frontmatter order), write the migration, expose them through the patch types in repo.ts and the MCP tools.

How get_next ranks work

  1. Deadline risks, taken from the scheduler's at_risk.
  2. Priority, inherited through hierarchy.ts.
  3. Finish before starting: at equal priority, release beats verify beats build.
  4. Earliest deadline, then code order.

It also warns when too many milestones across all projects are in build at once (a WIP limit, default 3). Checks with a task: become tagged tasks, so review and QA land on the schedule next to feature work.

Hooks

EventWhat it does
SessionStartpm-flow brief: map the git remote to a project, run the detectors, send signals, print the brief and this stage's rules. 3 s timeout; a failure never blocks the session
PostToolUseAfter test commands (npm test, vitest, pytest…), record pass or fail for verify.tests
PreToolUseGuards: edits to applied migrations, push to main, code before spec (off, warn or ask per playbook)
StopLight reminders: log time on the task in progress; “all M5 tasks done, run /sdlc:verify”

Board page

/lifecycle shows projects as rows and stages as columns. Milestone cards show their open checks and the next action, with a personal/company filter. The project page gets a one-line stage strip.

How it grows

A project's check list comes from four sources, and every check keeps its source, so you can always see why a gate exists.

  1. Playbook. The base and overlay checks, for example spec.accepted from sdlc@1.0.

  2. Detectors. When the repo changes shape, checks and rules get added: migrations/, vercel.json, a Dockerfile, an openapi.yaml. Source: detector:migrations.

  3. Retros. /sdlc:retro turns what went wrong into project checks and rules. Source: learned:PMA-M3.

  4. Promotion. When a learned check holds across projects, move it into the playbook and bump the version. Every project picks it up at the next sync.

Out of scope & risks

  • No workflow engine. No BPMN or generic state machines. The engine knows stages and checks and nothing more.
  • No LLM when checks are evaluated. Evaluation is deterministic and tested. Models do the judgement work: specs, reviews, retros.
  • Nothing written into company repos by default. Projects are found by git remote. Rules are copied only on request and kept out of git.
  • Risk: slow session start. The brief has a 3 s timeout, caches the last result, and never blocks the session.
  • Risk: check fatigue. Keep the base playbook to about a dozen checks. Waiving is one call, but always recorded with a reason.
  • Risk: plugin features change. Keep the plugin thin and the logic in my_pm, which you control and test.
