Playbooks & Lifecycle

Every project follows the same lifecycle, from idea through release to learn, with an optional maintain stage. Each project has its own playbook for how it runs that lifecycle: rules, skills, hooks, checks and environments, versioned like code so you can roll back. my_pm tracks each project's status and tells you what to do next across all of them.

Summary

  • Lifecycle is the fixed sequence every project follows: idea, spec, design, plan, build, verify, release, learn, and optional maintain. Its principles don't change.
  • Playbook is one project's way of running the lifecycle: its rules, skills, hooks, checks, conventions and environments. It is built from shared layers (sdlc, personal or company) plus the project's own parts, and it lives in one private git repo.
  • Everything is versioned. A playbook change is a commit with a version bump and a changelog line. my_pm pins each project to a version, so rolling back is one call.
  • Status lives in my_pm: each milestone's stage, its checks, and which environments it has reached. A pure, tested engine turns that into ranked next actions and warnings across all projects.
  • Rules come first. Every stage skill shows the project's rules and asks you to confirm before it acts. A project without rules is flagged until it gets some.
  • Build it in slices. PMA-M6 (lifecycle core in my_pm) is useful on its own: any Claude session can ask what's next across your projects.

Project rules

Rules are project scope. Nothing runs on a project without you seeing its rules first.

What counts as a project's rules

  • Repo rules the repo already has: CLAUDE.md, AGENTS.md, .claude/rules/**. my_pm's CLAUDE.md has 7.
  • Playbook rules in projects/<CODE>/rules/. They cover company repos too, where you don't want files in the repo.
  • Layer rules for the current stage, from sdlc, personal or company.

The check before a skill acts

  1. The skill runs pm-flow rules --stage <stage>, which lists the rules that apply, with their source and version.

  2. It shows you the list and asks: Apply these rules, Edit rules first, or Cancel. It asks once per session, and again whenever the rules change (D6).

  3. If the project has no playbook rules and no repo rules, the skill stops and offers /sdlc:rules to write some, or to continue with layer rules only.

Hooks can't hold a conversation, so they surface rules instead: the SessionStart brief lists them, and PreToolUse guards enforce the hard ones.

Warnings in my_pm

Warnings are computed, not stored. They show at the top of get_next, in get_overview, and on the board.

Environments

Each project builds one piece of software and ships it through its own environments.

  • Declared in the playbook, in promotion order. The default is dev → staging → prod; PMA uses dev → prod. Each entry can name its database, app target and URL.
  • Release is promotion. A milestone in release moves through the environments in order. It leaves release once it has reached the last one and that environment's checks pass.
  • Checks can target one environment (env: prod): rollback plan, migration paired with the deploy, company sign-off.
  • Deploys are recorded per milestone with evidence such as commit, URL and time, by /sdlc:release or by deploy_signals when a matching command succeeds. Recording prod before staging needs a waiver.
  • Drift is visible. The board shows what each environment runs, for example “dev is 1 milestone ahead of prod”.

Versions & rollback

Playbooks change the way code does: in commits, with versions, and with a way back.

WhatVersion lives inHow you roll back
Project playbookprojects/PMA/playbook.yaml, changelog, tag PMA@1.1.0/sdlc:rollback PMA 1.0.0 re-pins the old version in my_pm and reverts the commit
Layerlayers/sdlc/layer.yaml, tag sdlc@1.2.0Projects keep their pin until they adopt; revert and release a patch version
Plugin (skills, hooks)plugin.json version, tag plugin-sdlc@0.4.0Check out the tag in the repo and update the plugin
Adapted skillsPart of the plugin versionSame as the plugin; make upstream-diff for upstream changes

The maintain stage

  1. /sdlc:retro ends with proposals, for example “spec template needs a data-migration section” or “add a release check for Vercel env vars”.

  2. /sdlc:maintain turns the proposals you accept into edits to the project playbook, or to a layer when they're general. Examples: idea conventions, how paths are built, spec schema and format, build tools, the verify process, release checks, or an adapted skill.

  3. Each accepted change becomes one commit with a version bump and a changelog line. pm-flow sync sends the new version to my_pm, and the project is re-pinned (D9 covers layers).

  4. Unhappy with it? /sdlc:rollback pins the previous version and reverts the commit. Past check results stay in the history.

my_pm never deletes a playbook version, so a pin can always point back. Skills and hooks follow the plugin installed on the machine; checks and rules follow the project's pin.

Company work

Following D1 (metadata and links only) and D2 (private repo, files or zip).

  • What my_pm stores for a company project: code, stages, check keys and results, deploys per environment, links to the company tracker and repo. No specs, no rule text, no check descriptions.
  • Where the rules live: layers/company/ and projects/<CODE>/ in the private repo. The brief reads them from your local copy.
  • Installing on the work machine: make zip, unzip, then register the folder as a directory marketplace. No public URL anywhere.
  • Nothing in company git: projects are matched by git remote, plugins are enabled in .claude/settings.local.json, and any copied rules go in .git/info/exclude.

How get_next ranks work

  1. Deadline risks, from the scheduler's at_risk.
  2. Priority, inherited through hierarchy.ts.
  3. Finish before starting: at equal priority, release beats verify beats build.
  4. Earliest deadline, then code order.

It also warns when too many milestones are in build at once (a WIP limit, default 3). Checks with a task: become tagged tasks, so review and QA land on the schedule next to feature work.

How it grows

A project's checks come from four places, and every check keeps its source, so you can see why a gate exists.

  1. Layers. Base and layer checks, for example spec.accepted from sdlc@1.0.

  2. Detectors. When the repo changes shape, checks and rules get added: migrations/, vercel.json, a Dockerfile, an openapi.yaml. Source: detector:migrations.

  3. The project playbook. Checks and rules written for this project, often after a retro. Source: PMA@1.1.0.

  4. Maintain. Changes that prove general move into a layer as a new version, and every project that adopts it gets them.

Out of scope & risks

  • No workflow engine. No BPMN or generic state machines. The engine knows stages, checks and environments, nothing more.
  • No LLM when checks are evaluated. Evaluation is deterministic and tested. Models do the judgement work: specs, reviews, retros, playbook proposals.
  • No deploy automation. The release skill records and checks deploys; it doesn't run your pipeline.
  • Nothing written into company repos by default. Projects are matched by git remote; copied rules are excluded from git.
  • Risk: too many prompts. Rule confirmations and guards can pile up. D6 and D3 keep them in check.
  • Risk: adapted skills drift from upstream. make upstream-diff keeps the gap visible.
  • Risk: slow session start. The brief has a 3 s timeout, caches its last result and never blocks.
  • Risk: plugin features change. The plugin stays thin; the logic lives in my_pm and pm-flow, which you control and test.
