## Goal
Move persistence from markdown files (local `./data` / private Vercel Blob) to Neon Postgres, so reads are a handful of queries instead of listing + fetching every file, writes are transactional (no more `create`-retry id allocation or half-applied batches), and the data can be queried directly.

## Current state
- All persistence goes through `src/lib/repo.ts` → `FileStore` (`list/read/write/create`), with `FsStore` and `BlobStore` backends picked in `src/lib/store/index.ts`.
- `loadWorkspace()` lists and parses every `tasks/`, `features/`, `projects/` markdown file on each call; ids come from scanning file names + `create` conflict retries (`createWithNextId`).
- `createTasks` writes one file per task, then rewrites some to resolve forward refs — not atomic.
- `.env` already has `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `NEON_BRANCH`; `neon.ts` + `@neon/config` exist but are unused.

## Approach
- Relational schema (`projects`, `features`, `tasks`, `settings`) with columns mirroring the zod schemas in `src/lib/types.ts`; markdown **body stored as a `text` column**, not as a file — Postgres holds structured content only, never the raw `.md` files themselves (no file/blob storage in Neon).
- Extract a `Repository` interface from `repo.ts` so the public functions (and MCP tools / UI) don't change; keep the file backend for local/offline use and tests, add a Postgres backend.
- Rows are parsed through the same zod schemas, so types and defaults stay single-sourced in `types.ts`.
- Serverless driver (`@neondatabase/serverless`) over the pooled URL at runtime; unpooled URL for migrations.
- **Migration task (`PMA-M3-T8`):** a one-shot import script that reads every project/feature/task through the existing file-based repository — parsing each `.md` file into its typed fields (id, title, status, priority, deadline, body text, tags, `depends_on`, etc.) — and inserts those as relational rows in Postgres, in dependency order, resetting id sequences to the migrated max. The source `.md` files are read and then left in place (or exported back to for backup/rollback); they are never uploaded or stored as files/blobs in Neon. `PMA-M3-T9` provides the reverse (Postgres → markdown) for backups/rollback.

## Out of scope
- Changing the domain model, MCP tool shapes or scheduler.
- Neon Auth / moving PMA-M1 Auth onto Neon.
- Multi-user / row-level security.
- Storing original markdown files (or any file/blob) inside Neon — content is migrated, not files.

## Acceptance criteria
- With `DATABASE_URL` set, the app and MCP server read and write only Postgres; `get_overview` reports `storage: "postgres"`.
- The same repo test suite passes against both the file backend and Postgres.
- `createTasks` is atomic: a failing batch leaves no partial tasks; ids stay `T-n` / `F-n` / `PRJ-n` and continue from the migrated max.
- Importing the current `data/` yields identical `loadWorkspace()` output (ids, fields, bodies, order) and the same `get_schedule` — as relational rows in Postgres, with no `.md` files or raw file blobs written to Neon.
- Production cut over on Vercel with a documented rollback path; `npm run typecheck && npm run lint && npm test && npm run build` pass.
